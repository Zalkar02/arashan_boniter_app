# ТЗ: развитие Arashan Boniter (после MVP)

## Цели
1. Установка и обновление, которые может сделать любой пользователь, без терминала, git и Python.
2. Версионность приложения: пользователь и сервер знают версию, устаревшие версии можно заблокировать.
3. Быстрый поиск по БД, включая кириллицу и подстроки (триграммы).
4. Подготовка кода к большому числу новых функций.

Платформы: Windows 10/11 и Linux Mint. Аудитория: 20–30 пользователей, релизы по необходимости.

## Принятые решения
| Вопрос | Решение |
|---|---|
| Linux-формат | AppImage (автообновление без прав администратора). `.deb` позже, при необходимости |
| Windows-формат | Установщик Inno Setup, установка без прав администратора, ярлыки на рабочем столе и в меню |
| Подпись Windows | Пока без подписи. В инструкции: «Подробнее → Выполнить в любом случае». Подпись можно добавить позже |
| Хранение релизов | S3 UpCloud, бакет с публичным чтением, запись только у CI |
| Репозиторий | Остаётся приватным, GitHub Releases не используются |
| Сборка | GitHub Actions по тегу `vX.Y.Z` |
| Данные пользователя | Вне папки приложения (`%LOCALAPPDATA%\ArashanBoniter`, `~/.local/share/arashan-boniter`), обновление их не трогает |

## Проверка версии: manifest.json или API сервера
Рекомендация: **manifest.json в S3 как основной источник**, плюс жёсткая защита на стороне API.

- **manifest.json (S3)**: доступен без авторизации и при недоступном API, не нагружает сервер, меняется самим релизом (CI кладёт его последним, после файлов). Содержит `version`, `min_supported_version`, `notes`, ссылки и sha256 для каждой платформы.
- **API сервера**: приложение передаёт свою версию в заголовке (например, `X-App-Version`). Если протокол синхронизации несовместим, сервер отвечает `426 Upgrade Required`, и приложение показывает окно обязательного обновления. Это страхует от случая, когда пользователь не проверил обновления, а формат синхронизации уже изменился.
- Только API (без манифеста) не подходит: нужен код на сервере для раздачи ссылок, и проверка не работает до входа в аккаунт.
- Статус: манифест реализован; заголовок версии и обработка 426 — **в плане** (требуют изменений на сервере).

## Формат manifest.json
```json
{
  "version": "1.3.0",
  "min_supported_version": "1.0.0",
  "notes": "Что нового",
  "platforms": {
    "windows": {"url": "...", "sha256": "...", "size": 123},
    "linux":   {"url": "...", "sha256": "...", "size": 123}
  }
}
```

## Поведение приложения
- При запуске (через 2 секунды) тихая проверка; ошибки сети не показываются, работа офлайн не блокируется.
- Кнопка «Проверить обновления» в настройках; версия видна в настройках.
- Доступно обновление: окно с описанием, «Обновить сейчас» / «Позже».
- Версия ниже `min_supported_version`: только «Обновить сейчас»; отказ или ошибка закрывает приложение.
- Установка: скачивание с прогрессом, проверка sha256, замена AppImage (Linux) или запуск тихого установщика (Windows), перезапуск.
- Запуск из исходников (разработка): автообновление отключено, только уведомление.

## Процесс релиза
1. `./release.sh X.Y.Z "что нового"` — меняет `version.py`, коммитит, ставит аннотированный тег, пушит.
2. CI проверяет совпадение тега и `version.py`, собирает AppImage и Windows-установщик.
3. CI загружает файлы в S3, затем `manifest.json` (`min_supported_version` берётся из файла `MIN_SUPPORTED_VERSION`).
4. Секреты GitHub: `S3_ACCESS_KEY`, `S3_SECRET_KEY`, `S3_ENDPOINT`, `S3_REGION`, `S3_BUCKET`, `UPDATE_BASE_URL`.

## Критерии приёмки этапа 1
- Установка на чистой Windows и на Linux Mint без терминала.
- Обновление 0.1.0 → следующая версия одной кнопкой, данные сохраняются.
- Повреждённый файл (неверная sha256) не устанавливается.
- Версия ниже минимальной получает обязательное окно обновления.
- Приложение работает без интернета и не падает при недоступном сервере обновлений.

## Этап 3. Поиск и оптимизация БД (подробно)

**Проблемы сейчас**
- `ilike '%...%'` по 8 колонкам: полное сканирование таблицы без индекса.
- Для кириллицы `find_owners_page` грузит все строки в Python и фильтрует там.
- `COUNT` и выборка отдельными запросами; в коде около 45 мест с `.all()` / `like`, часть из них на больших таблицах.

**Что делаем**
1. **Бенчмарк до правок:** генератор 100 тыс. владельцев и овец, замеры основных запросов (поиск владельца, поиск овцы по `id_n` и кличке, история, список в «Базе данных»).
2. **FTS5 с триграммами** (`tokenize='trigram'`): виртуальные таблицы для владельцев (имя, логин, город, адрес) и овец (кличка, `id_n`). Работает по подстроке и кириллице; синхронизируются триггерами. Телефон ищется по отдельной колонке `phone_digits` (только цифры) с индексом.
3. **Нормализация:** `name_norm` и `nick_norm` заполняются всегда при записи и при синхронизации, а не только миграцией.
4. **Индексы** на реальные фильтры: `is_deleted`, `synced`, `updated_at`, `sheep(owner_id, is_deleted)`, `owners(sheep_id, owner_bool)`, `applications(sheep_id, date)`.
5. **Выборки:** пагинация только в SQL (`LIMIT/OFFSET` или keyset), никакой фильтрации в Python; убрать N+1 (`joinedload/selectinload`); общий `COUNT` по необходимости.
6. **Нечёткий поиск** (опечатки) — по желанию, `rapidfuzz` поверх кандидатов из FTS.
7. Индексы и FTS создаются миграциями (этап 2), с заполнением для существующих записей.

**Ограничения, которые нужно знать**
- Триграммный поиск работает от 3 символов; для 1–2 символов используется обычный префиксный поиск по индексу.
- Цель по скорости: поиск по 100 тыс. записей быстрее 50 мс на среднем компьютере. Цифра будет подтверждена бенчмарком, а не обещана заранее.
- Скорость синхронизации и печати PDF этим этапом не решается; для них отдельные замеры.

**Приёмка:** бенчмарк «до/после» в репозитории; поиск не вешает интерфейс на 100 тыс. записей; результаты поиска совпадают со старым поведением на тестовых данных.
